# 材料整理中的失败与修正

本文件记录本阶段真实整理失败，不替代解题原始记录或失败测试。时间与原命令输出可在本阶段主会话 `01a143f4-3a36-78a0-a6e2-8b599d476dc4` 读取。

1. 工作流脚本首次查询了不存在的 `register --help` 子命令，工具返回 argparse exit 2。根据实际帮助改用 `session` 完成登记，没有据此创建虚假会话。
2. 初版轨迹导出错误地优先 `session_meta.session_id`。独立验证发现子会话可继承根值，导致三份主会话导出被子会话内容覆盖。修正为自身 `session_meta.id`，从原件重新导出全部15个会话；同时保留真实 `codex_engine_session_id`，新增逐文件metadata自身ID验证。没有伪造丢失主记录，也没有用摘要替代它们。错误导出属于可重新生成的派生文件，修复后的副本取自原始日志。
3. 第一次、第二次完整patch应用比较均失败：missing=[] / extra=[]，部分LF文件被Git进程继承的换行配置转成CRLF。第二次失败详细摘要保存在 `patch-roundtrip-failed-v1.json`，原命令与退出1保留在原生会话；没有把“apply命令退出0”当作全文件一致。没有改源工程的换行符或Git配置。最终临时clone中的Git命令显式携带 `-c core.autocrlf=false -c core.eol=lf`，再执行checkout、apply检查、实际apply及完整SHA比对，753项全部一致，见 `../changes/patch-validation.json`。
4. 独立验证发现材料校验器的Windows路径正则会误认URL，以及官方索引四个标题存在标点/括号差异。修正路径边界，并按官方24个标题逐字生成；最终校验覆盖原字段、真实包内路径、原生会话ID、日志、补丁与源指纹。这些是材料工具修正，未改业务断言或测试结果。
5. 二进制清单复查发现工程 `test-harness/harness/__pycache__` 有三份Git可见的旧Python字节码缓存。它们不属于交付源码或原始执行日志；仅从封存副本选择器排除，源缓存未删除或改写。过滤前的753项成功比对摘要保存在 `patch-validation-before-cache-filter.json`，该旧树不作为最终版本；重新生成后的750项工程树为 `93dafec8eb504b56d1329df5e5ad59110c66d27e`，再次check/apply和全文件比较通过，二进制75项均已明确为官方同源资源或本题本地测试证据。
6. 最后刷新原生轨迹后，Skill读取索引误把新增说明文字中的裸文件名“Get-Content SKILL.md”算作一次读取。仅调整辅助索引器为显式带路径的读取候选，排除裸文件名的歧义提及；恢复为19条、5个路径。该索引器因此与独立审计表中的旧hash不同，最终工具摘要以材料manifest为准；封存工程、补丁、正文、所有原生轨迹均未由此改写，已重新做脚本AST和材料校验。

本阶段没有重跑业务构建/设备测试，没有更改生产代码、资源、配置或源Git索引/历史。原始run01–04失败、中断和oracle修订全部保留，不能用本文件解释取代原始证据。
