# 成果提交材料清单

适用于线上初赛和线下决赛，依据章程第 5.9 条、第 5.12—5.19 条。每道作答的赛题都须使用 AI 辅助研发；每道提交评分的赛题都须说明 AI 参与的环节并提供对应原始记录，不能用其他题目的记录或无关对话替代。

每次须提交一个完整 ZIP 文件；同一记录可只保存一份，用相对路径交叉引用。下列目录为推荐组织方式，各题材料的路径以 `submission.json` 为准。

| 材料 | 是否必交 | 内容与推荐位置 |
| --- | --- | --- |
| 1. 任务清单 | 每次必交 | 根目录 `submission.json`：团队、阶段、版本、联系人和本阶段全部题目；`submitted` 任务填写工程、构建说明及记录索引路径；`not_completed` 也须保留 |
| 2. 完整工程 | 每个 `submitted` 任务必交 | `tasks/<题目ID>/project/`：源码、资源、必要配置、依赖清单及锁文件；不能只交安装包或补丁 |
| 3. 构建运行说明 | 根目录说明及每个 `submitted` 任务必交 | README.md 说明公共环境；`tasks/<题目ID>/build.md` 说明依赖安装、构建、安装、启动、应用标识和必要初始化；不能依赖未提交文件或参赛电脑私有路径 |
| 4. 基线至最终版本的变更 | 每个 `submitted` 任务必交 | 推荐 `tasks/<题目ID>/changes/final.diff`，覆盖新增、修改、删除文件；在 `trace-index.md` 注明官方基线、最终版本标识和差异位置；二进制资源另列文件及摘要并保留实际资源 |
| 5. 人机协作方案与实际配置 | 每次必交 | `solution.md` 说明完成情况、协作方式、成员分工及来源保护措施；`system-config/` 保存实际自定义提示、Skill、工作流及配置变更，第三方组件注明版本和获取方式；无自定义项也须提供配置说明 |
| 6. AI 原始记录 | 所有已发生的解题过程均须提供 | `traces/` 中保存相关主会话、子会话、工具调用及结果，包括失败、重试、未采用方案和已尝试但未完成任务；工具支持导出会话数据库时，提交相关数据库记录；否则提交 JSON、JSONL 等原生记录或等效的完整记录，并说明读取方式 |
| 7. 人工操作与代码修改记录 | 操作情况须说明；发生人工改代码时须附修改证据 | 推荐 `tasks/<题目ID>/human-changes.md`；按操作或修改批次说明谁改、为什么改、改哪些文件、前后版本和证据路径；附当时留存的编辑历史、差异、快照或版本控制记录。无直接改代码时注明“无人工直接修改代码”；人工提示可引用 AI 会话记录 |
| 8. 来源及记录索引 | 每次必交；已提交或已尝试任务须能定位记录 | 根目录 `sources.md` 列第三方来源，无则声明；各题 `trace-index.md` 关联 AI 记录、人工记录、版本、构建自测、脱敏与缺失说明。已尝试但未提交工程的题目，也在 `solution.md` 列出其索引路径 |

## 如何提交人工修改记录

- 以一次有明确目的的修改或调试操作为一条，可涉及多个文件；不要求记录每次按键、每行作者或每次保存，也不要求每次操作创建 Git 提交。
- 修改前后使用真实提交号、快照编号或文件摘要标识，并关联能读取的差异或历史证据；只有一句“某队员修复了问题”不够。
- `human-changes.md` 是索引和说明，不能替代当时产生的原始记录。可以在提交前整理索引，但不能事后伪造修改过程。工具实际保留的时间戳应保留。
- AI 与人工混合修改时如实注明，关联两类记录，不要求推算代码贡献百分比。
- `final.diff` 展示总体交付变化，不能单独证明哪些操作是人工完成的，也不能替代人工修改证据或完整工程。
- 无人工直接改代码的任务，无需额外创建人工修改专用空差异文件；每个 `submitted` 任务仍须提供总体交付差异（如 `final.diff`）。在 `trace-index.md` 明确说明，并引用已有提示、调试和方案选择记录即可。

## 未完成任务与共用记录

未尝试任务只保留清单条目并标记 `not_completed`，无需提供空日志。已尝试但未完成的任务仍须提交实际产生的记录，在 `solution.md` 列出题目 ID 及索引位置；即使 `submission.json` 的工程路径为空，也不能省略这些过程记录。

多个任务共用一份会话或配置时，可集中保存，各题索引注明对应会话、事件或记录范围，须能分别识别 AI 对每道题的实际参与；共用记录不等于可以仅在其中一道题使用 AI。

## 无需提交的内容与敏感信息处理

不要求全程录屏、逐键记录、未输入系统的思考、工具不输出的模型内部信息、AI 代码占比证明或与赛事无关的历史。不提交账号密钥、个人签名私钥、无关私人会话及整个客户端数据库。原始记录可按规则脱敏，须说明范围，不得遮蔽代码来源与修改依据。提交可独立读取的相关记录副本，不提交仍在写入的数据库临时文件。

可导出相关 Git 日志、补丁或快照作为证据，无须打包整个 `.git` 目录；导出的证据须覆盖实际提交版本及未提交到 Git 的改动。缓存、旧 ZIP 和无关工程不放入成果包。

## 核验与截止后的说明

线上初赛和线下决赛中，官方会逐题核验各队提交评分的赛题是否有 AI 实际参与研发。核验会检查原始记录是否对应本题及具体研发过程，不只检查文件是否存在。对拟入围、递补及有具体疑点的队伍进一步核查完整过程；决赛对全部队伍核查。

过程记录缺失时，官方会逐题核查。个别记录缺失，但冻结成果包内其他原始证据足以核验本题 AI 参与及相关来源、修改过程的，按实际测试结果正常计分，不因该缺失直接认定作弊。

在给予队伍说明机会并核查包内已有证据后，仍无法证明某题实际使用 AI 参与研发的，该题全部 F-point 均不计通过，仍计入总数，不直接将其他题目或整队成绩归零。

涉嫌伪造、故意隐瞒或其他违规的，按第 11.1 条、第 11.4 条查实处理；不得仅凭缺失推定存在故意行为。处理决定须列明涉及题目、事实依据及计分后果，并告知申诉渠道。

截止后，队伍可应核查要求解释已冻结材料并指出包内已有证据的位置，但不得补交代码、原本漏交的解题材料或以新产生的记录替代原始解题证据；解释须留档，不能作为新增成果参与评分。邮件收件、官方故障、计分错误等程序性申诉证据可按第 10.3 条提交，不属于新增参赛成果。

## 提交前核对

每次打包前，请停止本次提交涉及的人工修改和 AI 任务，保存代码与原始记录，并注明成果冻结时间。完成记录导出、材料整理、打包和校验后，再上传成果包并发送正式提交邮件。代码、配置、差异及过程记录须对应同一冻结版本。

提交后可继续作答；如需更新正式成果，须重新冻结并生成包含新增记录的完整成果包，在截止前重新发送正式提交邮件。未收到新的正式提交邮件时，仍以最后收到的正式提交邮件对应成果包为准，后续未提交成果不参与评分；不得直接替换已上传包中的文件。上述操作均须在规定作答及提交时限内完成。

已在截止前发送报名邮件、尚未取得团队 ID 的队伍，可使用“学校名称—队名”作为临时标识，由报名登记邮箱提交成果，并在邮件正文注明报名邮件主题及发送时间。正式提交邮件、成果包内 `team_id` 字段及相关材料使用同一临时标识；工作人员核对报名收件记录后关联正式团队 ID，不要求队伍为此改动已冻结成果包。临时标识不免除按时报名及提交的要求。

- 清单保留全部题目，所有相对路径指向包内真实文件。
- 完整工程与 `final.diff` 对应同一提交版本；新增文件、删除文件和资源变更均已覆盖。
- 人工修改、AI 会话、构建自测能通过索引对应到任务和最终代码。
- 失败、重试、未采用及已尝试未完成任务的记录均已保留；缺失和脱敏范围已说明。
- ZIP 生成后计算大小和 SHA-256，上传同一文件并检查下载权限；正式邮件包含阶段、团队 ID、版本号、联系人、下载链接及提取码、文件名、大小和 SHA-256。

本地 `check_submission.py` 仅检查成果包结构和文件路径是否存在，不能验证本清单内容是否填全、`final.diff` 是否完整或人工记录是否真实；请逐项核对本清单，确认材料完整。
