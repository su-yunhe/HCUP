# 调度状态与角色交接

派工前保存所依据的 Spec、需求、方案版本和代码指纹（HEAD、已暂存/未暂存差异，以及会参与构建或测试的未跟踪新文件内容哈希；HEAD 不能单独代表有改动的源码）。测试期间编码角色停止改源码。代码改变后判定哪些旧测试证据失效并要求重测。

## 状态

`state.json` 包含题号、目录、基线、Spec 哈希、阶段、总体状态、主/子会话 ID、已批准产物、代码指纹、失败摘要、未解决项及下一步。

阶段为 `setup / requirements / design / implementation / verification / acceptance`；总体状态为 `in_progress / waiting_user / blocked / local_validation_complete`。`waiting_user` 是确需用户决定；`blocked` 是明确外部阻碍且无可推进工作，须说明原因。这些是工作流字段，不代替运行器 goal 工具。

状态和事件的唯一写者为主 Agent。`workflow.py event` 追加事件并更新阶段/状态/下一步。每次转移记录理由与证据，旧报告用递增轮次保存，不覆盖失败记录。

```powershell
python D:\HarmonyDev\codex\skills\harmony-task-flow\scripts\workflow.py event --root 本题目录 --phase implementation --reason 'R3 空列表分支未处理，需求和方案无需变化' --next-action '编码修复后，自测 R3 和相邻导航回归' --evidence workflow/verification/round-02.json
```

## 角色产物

- 需求：编号 R1、R2……，对应 Spec 段落、前置条件、操作、可观察结果和边界；区分明确要求、推断、真实歧义。
- 方案：需求到改动位置的映射、接口/状态/数据流、文件范围、顺序、验证方式；有约束冲突时提供证据。
- 编码：完成的需求、实际修改文件、偏离方案及原因、执行的检查与真实结果；不替自测作最终通过结论。
- 自测：每条需求为 `pass / fail / blocked / not_run`，列环境、代码指纹、命令、退出码、日志/截图路径；失败包含复现、期望/实际、归因假设及证据。编译通过、静态阅读或演示用例通过均不足以证明整题通过。

子 Agent 返回结论、产物路径、证据、未解决项和建议下一步。主 Agent 审查并路由。子 Agent 不向用户发散提问、不直接派工、不自行创建新主对话。

## 验收与重新打开

当前源码的全部必需需求有实测证据，构建和必要回归通过，无未处理失败且记录可追溯，才能本地验收。环境限制未测到的项保留，不能标记全完成。

需求或代码变化、新失败出现时重新打开相关阶段，不抹去旧验收。测试疑似不符 Spec 时由需求角色核对后修正，不能随意放宽标准。

普通技术选择、可逆修改、局部修复和可查证的不确定性由调度者处理。只有实质目标冲突、不可推断的信息/凭证、必须用户操作/授权，或调查后仍无可行下一步时询问；说明卡点、尝试、选项和影响，不重复索要已授予授权。
