## final.diff 递归边界建议

### 已确认的要求与冲突

S:57 指定所有材料生成到 `.comate/submission-draft/`；S:61、77—81 同时要求 diff 与提交 `project/` 一一对应，并明确 `.comate/` 等过程文件属于完整变化。若把新生成的 `.comate/submission-draft/changes/final.diff` 自身再纳入 diff，则新增文件补丁需包含自身全部字节及补丁头，重新生成后又改变被记录内容，无法得到这个通常新增文本补丁的有限自包含结果。复制 traces、logs 进 staging 后再把 staging 当工程输入，也会重复膨胀。

官方 C:5 允许组织方式按 submission.json 确定，C:10—12 将工程、构建说明、差异作为相邻交付材料描述，C:60 要求相同提交版本，但没有明确要求把提交整理容器自身复制进 `project/`。因此“冻结工程投影 + 工程之外的整理材料”最符合可核验目的；这是解释建议，不应宣称官方已逐字豁免此目录。

### 建议主 Agent 采用的具体约束

1. 将 `.comate/submission-draft/` 定义为单题交付 staging，最终映射到 `tasks/cml-spec1/` 的材料区域；成果包 `tasks/cml-spec1/project/` 不复制该 staging 根。
2. 同一显式清单决定 diff 输入及最终 project 拷贝。清单覆盖实际业务文件、依赖/锁文件、spec、hypium_tests、workflow、原有本题过程记录及 staging 之外的 `.comate/` 文件；不得只使用 W 的生产文件指纹。
3. `.git`、构建缓存、旧 ZIP、无关工程及敏感密钥依官方 C:35—37 处理，逐类说明；真实必要文件不可用“缓存”泛化移除。二进制保留文件并列摘要。工程本身已忽略但又必须交付的文件也须进入清单。
4. 在冻结时把现有代码、配置及相关过程文件固定成可复制的不可变快照；之后生成的原生记录导出、报告、补丁与校验输出放入 staging。若后续继续修改工程范围内的 workflow、state 或本报告，需重冻并重生成，或将这些后续材料明确标为工程冻结后的整理记录并放在 staging，不能悄悄造成 project/diff 漂移。
