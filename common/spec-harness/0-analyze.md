# 输出一：spec/acceptance.md

对 Spec 里每个场景的每个步骤，逐条拆成验收项。每条包含：

| 字段 | 说明 |
| --- | --- |
| 编号 | 如 A1、A2，便于后续引用 |
| 来源 | 对应 Spec 的哪个场景、哪一步 |
| 证据等级 | `SPEC_EXPLICIT`（Spec 明文）／`REASONABLE_DERIVATION`（合理推导）／`UNCONFIRMED_ASSUMPTION`（待确认假设） |
| 原子行为 | 一句话描述这条要做什么 |
| 可观察结果 | Hypium 能断言什么：具体文字、组件、页面、状态、数据、请求 |
| 八个维度 | 入口／前置数据／用户动作／UI 结果／数据结果／网络结果／返回结果／边界条件，不适用的写"不适用"并说明理由 |
| 稳定选择器 | 该项需要哪些组件 id；基线缺失的标注"需在实现时补 `.id()`" |

额外要求：

- **边界条件要穷举**：空输入、纯空格、取消、关闭、重复点击、快速连点、无数据、最后一页、
  部分操作、请求失败、返回后重进、重启应用后重进。不适用的也要写明为什么不适用。
- **网络类需求必须画状态机**，明确每个用户动作是否触发请求、loading 与请求的绑定关系、
  请求结束后的状态恢复。不要留"点击后先改 UI 稍后补请求"的空间。
- **文案逐字摘录** Spec 原文，不要改写。
- 标 `UNCONFIRMED_ASSUMPTION` 的项要单独汇总，附上你的推荐处理方式和理由。

# 输出二：spec/baseline-notes.md

先构建并安装**未修改的基线**，启动应用实际操作一遍，然后记录：

1. **基线快照标识**：打 `git tag baseline-<题目ID>` 或记录 HEAD，写进文档。
2. **构建基线状态**：构建命令、是否成功、已有告警清单（后续用于对比是否引入新告警）。
3. **Spec 描述的入口当前在哪**：页面文件路径、路由名、跳转调用点（带 `文件:行号`）。
4. **相关现状**：页面组件、状态模型、数据模型、网络服务、本地存储的位置与写法。
5. **可复用的既有实现**：基线里相近功能用了什么数据结构、状态管理、路由方式。
   官方测试沿现有流程进入目标页面，因此优先复用而非另起一套。
6. **缺失项**：Spec 要求但基线完全没有的能力。
7. **前置环境需求**：是否需要登录账号、服务端、WebDAV、测试数据；本地能否满足，不能满足的明确指出。
8. **测试可观测性风险**：关键组件是否缺少稳定 id、是否存在同名文本导致选择器歧义。

# 要求

1. **不改代码**。发现基线有 bug 也只记录，不在本阶段修。
2. **不编造**。所有结论要给出文件路径和行号；没验证的标注"未验证"。
3. **区分事实与推断**。Spec 明文、代码实证、你的推测必须分开标注。
4. **先构建安装再写结论**，不要只读代码就断言入口在哪。
5. 歧义不要自行决定，列假设给我判断。

# 背景

评分单位是 F-point，评测分 = 通过的 F-point ÷ 本阶段全部 F-point × 100。
未提交、构建失败、崩溃、超时、跳过的都不计通过但计入分母。

正式测试脚本、隐藏输入、参考答案均不公开，线上期间没有官方反馈。
验收矩阵就是我们自己的"隐藏测试推导"——它的覆盖面直接决定能拿多少分。

Spec 场景数不等于官方 F-point 数量，不要据此推断分值。
