## 1. 需求范围、原文与判定口径

目标是补足恢复动作的**第一层确认**，使未选择、取消、系统手势关闭、点击外部关闭时均不进入下载或覆盖流程。Spec 没有给出第一层选择“继续”之后的完整业务规格，不能把既有下载、预览、第二次确认和实际导入升级为本题新增明文要求。

证据等级统一使用：

- `SPEC_EXPLICIT`：Spec 明文要求。
- `REASONABLE_DERIVATION`：为使明文可成立的合理推导；不得当成 Spec 原句。
- `UNCONFIRMED_ASSUMPTION`：Spec 与基线不能消除的未规定内容，见第 8 节；不混入核心通过条件。

### 1.2 数据与网络观测定义

- **P0（主测试前置）**：沿既有入口进入设置中的 WebDAV 区域；初始没有手动同步/备份/恢复进行；自动 WebDAV 同步关闭或已被验证角色隔离；记录页面初始状态与本地数据快照。主场景可使用有效配置和本地、云端不同的数据，以避免“没数据所以看不出覆盖”的假通过。
- **D0**：点击恢复前的本地学习记录、词条状态、用户词书等可被恢复导入改变的数据快照。至少准备一个仅本地存在或本地值不同于云端的标记数据。配置输入、结果区、按钮状态另记为 UI0；有既存结果文字时也要保存初值。
- **N-download=0**：本次恢复动作导致的云端备份 GET/正文下载次数为 0。下载入口调用记录可作门禁的辅助证据，不绑定具体方法名，也不能用调用记录代替实际请求计数。Spec `:27`、`:41` 明确要求“不下载”；不能以最后没导入代替这一断言。
- **N-restore=0**：本次恢复动作导致的 WebDAV 请求总数为 0，包含目录/备份 HEAD、探测、创建、GET 等。此项是第一层仍在等待确认的合理推导，强于单纯 `N-download=0`，须分别标级。
- **W-import=0**：本次恢复没有导入/覆盖造成的用户数据写入；D0 与操作后/重进后数据相等。可通过导入调用记录辅助确认未进入恢复流程，但不要求采用具名函数或特定测试钩子。无副作用还可结合快照/manifest 写入计数辅助检查，但全应用文件时间戳不适合作为唯一断言。
- **请求归因**：网络计数限定本次恢复动作，并记录计数窗口；启动/进入前台可能触发独立自动同步（`EntryAbility.ets:53-54`，`AutoWebDavSyncManager.ets:33-65`），不能把后台请求误算成本次恢复请求。应先隔离自动同步再清零计数；不需要为本题禁止整个应用的所有网络活动。
- **UI0**：第一层对话框出现前的配置输入、同步/备份结果区、按钮文案与可用性。取消后恢复 UI0，不能将初始已有结果强制清空，也不能以新增取消成功结果替代“保持不变”。
- **loading**：表示正在执行恢复请求/处理的用户可见忙碌态（例如基线 `webdavBusy` 导致的按钮文字变化与禁用、结果区处理中）。确认框自身的“等待选择”与请求 loading 分开；为防重入而设置的内部确认中标志不等于已发起请求。Spec 没要求第一层背后所有按钮在弹框期间仍可点击，但要求取消后可点击。
- “立即”按点击后可观察到的第一个稳定 UI 状态判断：必须先出现第一层确认，不能等待配置校验后的网络完成、下载、解密或预览后才显示。Spec 没有毫秒数；测试等待上限是测试设施参数，不得写成产品需求。

## 5. 网络动作与 loading 状态机

图中的状态和防重入标志是行为模型，不强制采用某个状态变量、锁或弹框 API；N-restore=0 的证据等级仍是 R20 的合理推导。下面的前半段覆盖核心确认门禁：第一层状态没有恢复请求。后半段仅说明继续向基线流程交接的位置，便于防止在确认前改 UI 后悄悄发请求；不把基线后续细节写成 Spec 明文。

```mermaid
stateDiagram-v2
    [*] --> Idle
    Idle --> Confirm1: 点从云端恢复 / 请求0; 请求loading=off; 进入确认中
    Confirm1 --> Confirm1: 不选择或重复点恢复 / 请求0; 不进入恢复; 至多一框
    Confirm1 --> Idle: 点取消 / 请求0; W-import=0; 关闭; UI0; 结束确认中状态
    Confirm1 --> Idle: 系统返回手势 / 请求0; W-import=0; 同取消
    Confirm1 --> Idle: 点弹框外部 / 请求0; W-import=0; 同取消
    Confirm1 --> Handoff: 点继续一次 / 交接一次; 此前请求0
    Handoff --> ExistingFlow: 既有恢复入口 / 请求与loading从实际任务开始绑定
    ExistingFlow --> Idle: 后续完成、取消或失败 / 任务结束释放busy与loading
```

| 动作/事件 | 恢复请求 | loading/按钮约束 | 数据/终态 | 证据等级与范围 |
| --- | --- | --- | --- | --- |
| 打开设置、展开 WebDAV | 本题不要求主动恢复；可能独立触发应用前台自动同步，须隔离 | 保留原空闲 UI | UI0/D0 测试前建立 | 基线入口事实；非新增恢复请求授权。 |
| 首次点恢复 | N-download=0；推导 N-restore=0 | 立即第一层；不得以正在下载阻塞弹框。内部确认防重入可独立于请求 busy | 不覆盖 | R02/R07/R08/R09/R20。 |

| 重复/快速点恢复 | 无新增恢复请求 | 不堆叠确认，不越级，确认锁不视作网络 loading | 仍一层 | R22 推导。 |

| 外部区域关闭 | 与点取消相同 | 与点取消相同 | 与点取消相同 | R13/R14-R21。 |

**静态风险**：现有 `runWithTimeout` (`SettingsSyncSection.ets:115-121`) 是 `Promise.race`，没有在胜出时清理 timeout，也没有取消底层任务。第一层不应进入此下载 timeout 包装，从源头避免“已取消但底层仍继续”。不要以“UI busy 已恢复”推断请求被取消。本阶段只记录，不修代码。
