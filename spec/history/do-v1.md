# 要求：
这个开发要求很高。不能只追求“完成基本的功能”，不能只做视觉效果，网络请求、状态持久化、页面返回、数据更新和边界条件都可能是独立检查点。最终的目标是在比赛中通过更多的测试点，取得更高的分数。因此，需要你全面考虑：每个开发需求的：
- 入口	测试从哪个页面、哪个按钮或哪种初始状态开始？
- 前置数据	需要登录、地址、商品、歌曲、配置或服务端数据吗？
- 用户动作	测试会点击、滑动、输入、返回、重启还是重复操作？
- UI 结果	必须出现什么文字、组件、页面、状态或布局？
- 数据结果	是否要保存、删除、排序、追加、同步或持久化？
- 网络结果	是否必须真的发请求？请求何时发起？
- 返回结果	返回后状态是否保持？滚动位置是否保持？
- 边界条件	空输入、取消、重复点击、没有更多数据、部分购买等如何处理？

怎么判分
核心单位是 F-point（Feature Checkpoint，可执行功能检查点）：一个 Spec 归一化后对应的一个可判定的 Hypium 测试方法。

线上评测分 = 通过的 F-point 数 ÷ 该阶段 F-point 总数 × 100（官网"评测分与未完成任务如何计算"）。
关键点：未提交、未完成、构建或安装失败、崩溃、超时、跳过、未执行的对应 F-point 都不计通过，但仍然计入分母——所以"没做"和"做崩了"都是实打实扣分。

由于正式测试脚本、隐藏输入、参考答案不公开，所以你必须在开发时考虑周全。
